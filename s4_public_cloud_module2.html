Section 2-1
CO 통제의 두 레이어 — 계획과 통제는 다르다
SAC가 CO 비용 통제에서 하는 역할을 이해하려면, 먼저 "계획(Plan)"과 "통제(Control)"가 근본적으로 다른 레이어임을 명확히 해야 한다.
계획 레이어 (Plan Layer)
핵심 질문: 얼마를 쓸 것인가?
작동 시점: 지출 발생 이전 (사전)
데이터 저장소: ACDOCP
SAC의 역할: 계획 수립 · 시뮬레이션 · Write-Back
보고 목적: Plan/Actual 비교 분석
예시: "2025년 마케팅 CC 예산 5억 설정"
VS
통제 레이어 (Control Layer)
핵심 질문: 초과 지출을 막을 수 있는가?
작동 시점: 지출 발생 시점 (실시간)
데이터 저장소: ACDOCA + CO 통제 오브젝트
SAC의 역할: 없음 (S/4 CO 전담)
보고 목적: AVC · Budget Control · 차이 분석
예시: "예산 초과 시 구매 오더 차단"
핵심 오해 — SAC Write-Back ≠ 비용 통제
SAC에서 ACDOCP에 계획 데이터를 Write-Back하는 것은 "얼마를 계획했는가"를 S/4에 기록하는 행위다. 이것이 있어야 Plan/Actual 비교 보고서가 작동하지만, 그 자체로 지출을 막거나 경고를 발생시키지는 않는다. 비용 통제(차단·경고)는 CO 모듈의 Availability Control이 담당하며, SAC는 그 레이어에 개입하지 않는다.
SAC Planning — 계획 레이어
예산 입력 · 시뮬레이션 · Rolling Forecast · 승인 워크플로우 → ACDOCP Write-Back
↕ SAP_COM_0087 / SAP_COM_0065
S/4HANA Universal Journal — 데이터 레이어
ACDOCA (실적) · ACDOCP (계획) · CO 오브젝트 (CC / IO / WBS / PC)
↕ CO 내부 엔진
CO 통제 엔진 — 통제 레이어
Availability Control (AVC) · Overhead Allocation · Variance Analysis · FM (Public Sector)
두 레이어가 함께 작동하는 방식
CC 예산을 ACDOCP에 설정(SAC Write-Back) → 실제 구매/회계 전기 발생(ACDOCA) → CO 엔진이 두 테이블을 비교하여 잔여 예산 계산 → AVC가 초과 여부 판단 → Fiori 보고서에서 Plan/Actual 표시.

SAC는 이 흐름에서 첫 단계(계획 설정)를 고도화하는 역할을 한다. 통제 엔진 자체를 대체하지는 않는다.
💬 고객사 CFO가 "SAC Planning을 도입하면 예산 초과 지출도 막을 수 있냐"고 묻습니다. 어떻게 답합니까? +
정확한 답변 구조: "SAC는 예산을 더 정교하게 수립하고 실적과 비교하는 데 탁월합니다. 그러나 지출 차단(Hard Stop)은 S/4HANA CO 모듈의 Availability Control이 담당합니다. Public Cloud Commercial 에디션에서는 Hard AVC 자체가 제한되므로, SAC 도입과 별개로 예산 통제 수준(Soft vs Hard)에 대한 의사결정이 먼저 필요합니다."

SAC Write-Back과 CO AVC를 혼동하여 "SAC 도입 = 예산 통제 해결"로 답하는 것이 흔한 실수다.
Section 2-2
SAC가 보완하는 영역 — 그리고 여전히 안 되는 것
Module 1에서 확인한 Public Cloud CO 기능 한계 중에서, SAC가 실질적으로 보완하는 영역과 SAC로도 해결되지 않는 영역을 명확히 구분해야 한다.
✅ SAC가 실질적으로 보완하는 영역
📊계획 수립 고도화 — S/4 Fiori 앱보다 훨씬 유연한 Top-Down / Bottom-Up 예산 편성, 시뮬레이션, 버전 비교
🔄Rolling Forecast — S/4 단독으로는 어려운 월별·분기별 동적 예측 재계산을 Data Action으로 자동화
📈Plan/Actual 시각화 — CC / PC / WBS 단위 계획 대비 실적을 Story 대시보드로 경영진에게 즉시 제공
🤝승인 워크플로우 — 부서별 예산 입력 → 검토 → 확정의 협업 프로세스를 S/4 외부에서 관리
🧮Costing-Based 수익성 분석 대체 — S/4 Public Cloud에서 미지원인 Costing-Based CO-PA를 SAC Story에서 유사하게 구현
❌ SAC로도 해결되지 않는 영역
🚫Hard AVC (예산 초과 차단) — 구매 오더·회계 전기 차단은 CO AVC 전담. SAC는 개입 불가
🚫Iterative Allocation — 순환 배부 로직은 S/4 CO 엔진 내부 처리. SAC Data Action으로 근사 구현은 가능하나 표준 아님
🚫FM Availability Control — 자금 용도 제한·이월예산·커미트먼트 관리는 FM 모듈 전담. SAC 범위 밖
🚫Activity-Based Costing — Activity Type 기반 내부 서비스 원가 계산은 CO-OM 엔진 내부 처리
🚫실시간 커미트먼트 통제 — PO·PR 발행 시점의 예산 잔액 실시간 차감은 CO 통제 레이어 전담
컨설턴트 포지셔닝 원칙
SAC를 제안할 때 "CO의 한계를 SAC가 메운다"는 식의 과장은 금물이다. 정확한 포지션은 "CO 통제 엔진 위에서 계획·가시화·협업 레이어를 강화한다"는 것이다. 고객사가 원하는 것이 "지출 차단"인지 "계획 고도화"인지를 먼저 구분하고, SAC의 역할 범위를 명확히 설정해야 한다.
Module 1 확인 한계 SAC 보완 가능 여부 SAC의 역할
Costing-Based CO-PA 미지원 부분 보완 Account-Based 실적 + SAC 모델에서 수익성 시뮬레이션
Hard Budget Control 제한 불가 계획 초과 시각화 · 알림은 가능, 차단 불가
Iterative Allocation 미지원 근사 구현 Data Action으로 배부 로직 구현 (표준 아님, 검증 필요)
FM AVC 미지원 (Commercial) 불가 예산 소진율 대시보드 제공은 가능, 통제 불가
복잡한 Variance Category 부분 보완 SAC Story에서 커스텀 차이 분석 시각화
Rolling Forecast 부재 완전 보완 SAC Data Action 기반 자동 재계산이 핵심 강점

💬 고객사가 "SAC에서 코스트센터 예산을 편성하고, S/4 보고서에서 예산 대비 실적을 바로 보고 싶다"고 합니다. 어떤 통신 시나리오 조합이 필요합니까? +
SAP_COM_0087 + SAP_COM_0065 조합이 필요하다.

SAP_COM_0087: SAC에서 편성한 CC 예산을 ACDOCP에 Write-Back → S/4의 "Cost Centers - Plan/Actual" Fiori 보고서에 계획 수치 활성화.
SAP_COM_0065: ACDOCA 실적 데이터를 SAC Story에서 Live 조회 → SAC 내에서도 계획 vs 실적 비교 대시보드 구성 가능.

두 시나리오 모두 S/4HANA Cloud Communication Arrangements에서 설정하며, Datasphere는 불필요하다.
Section 2-4
ACDOCP Write-Back 매핑 실전 — 5대 주의사항
SAP_COM_0087을 통해 ACDOCP에 Write-Back할 때 가장 많은 오류가 발생하는 지점이 매핑이다. 5가지 주의사항을 완전히 내재화해야 한다.
매핑 항목
SAC → ACDOCP 필드
핵심 주의사항
위험도
① Plan Version
SAC Version → VERSN
SAC Plan Category와 S/4 Plan Version(VERSN)은 별개 체계. 미매핑 시 데이터는 전기되나 S/4 표준 보고서에 나타나지 않음. 중앙 매핑 테이블 필수.
HIGH
② Cost Element
SAC Account → KSTAR
Primary CE / Secondary CE / Statistical CE 구분 필수. Statistical CE 전기 시 CO 원가 집계 제외. 비활성 CE 전기 시 API 오류 발생.
HIGH
③ Period
SAC Time Dim → POPER
YTD 누계 방식 Write-Back 시 중복 계상 발생. 반드시 월별 증분 방식으로 설계. 재전기 전 기존 데이터 역전기(Reverse) 선행 필수.
HIGH
④ 통화
SAC Amount → HSL/KSL
SAC 모델 단위(예: 백만 원)와 ACDOCP 원화 단위 불일치 시 금액 1/1,000,000 오류. Scale Factor 변환 및 HSL(회사통화)/KSL(CO통화) 분리 처리 필요.
MID
⑤ Record Type
고정값 → VRGAR='F'
VRGAR은 반드시 'F'(원가계획) 고정. SAC 모델에 없는 필드이므로 API 호출 시 상수값으로 주입. 임의 변경 시 CO 문서 인식 오류.
MID
가장 흔한 실수 — Plan Version 매핑 누락
"Write-Back 성공으로 표시되는데 S/4 Plan/Actual 보고서에 계획이 안 보인다"는 증상의 원인 1순위. SAC Plan Category ID를 그대로 VERSN에 주입하면 S/4가 인식하지 못하는 버전 코드가 된다. S/4 Communication Arrangements 설정 시 Plan Category ↔ VERSN 매핑을 반드시 명시적으로 구성해야 한다.
Period 중복 계상 시나리오
1월 계획 100만원을 YTD 누계로 매월 Write-Back하면: 2월 Write-Back 시 1~2월 누계 200만원이 전기되어 1월 잔액이 100 + 100 = 200만원으로 중복 계상된다. 예방 설계: 신규 전기 전 해당 VERSN + GJAHR + KOSTL 조합의 기존 데이터를 역전기(마이너스 전기)로 상쇄 후 재전기.
📝 확인 문제 — ACDOCP Write-Back 후 S/4 "Cost Centers - Plan/Actual" 보고서에 계획 수치가 전혀 나타나지 않는다. 가장 먼저 확인해야 할 항목은?
ASAC Planning 모델의 계정(Account) 차원 유효성
BSAC Plan Category와 S/4 Plan Version(VERSN) 매핑 정합성
CACDOCP 테이블의 HSL 금액 단위
DSAP_COM_0087 OAuth 토큰 만료 여부
Section 2-5
Closed-Loop 설계 실전 — 전 과정 연결
CO 비용 통제를 SAC로 가시화·계획화하는 완성된 구조는 4단계 순환 루프다. 각 단계의 기술적 연결과 실무 주의사항을 설계 관점에서 이해해야 한다.

STEP 01 주의
전년 실적을 SAC로 가져와 계획 기준선(Baseline)으로 사용. Live 조회 시 복잡한 집계 쿼리는 타임아웃 위험 → 주요 CDS View 사전 최적화 필요.
STEP 02 주의
SAC Plan Category와 S/4 VERSN 매핑 테이블을 Planning 시작 전 확정. 버전 체계 미확정 시 Write-Back 단계에서 전면 재작업.
STEP 03 주의
역전기(Reverse) 선행 → 재전기 구조 설계. 기간 Closed 여부 사전 확인. CE 유효성 사전 검증 로직 포함.
STEP 04 주의
S/4 표준 Fiori 보고서(Cost Centers - Plan/Actual)는 VERSN 기준으로 조회. SAC Story는 SAP_COM_0065 Live로 ACDOCA 실시간 반영.
이 루프가 완성될 때 가능해지는 것
① 경영진 관점: SAC Story 하나로 계획 대비 실적·예측 달성률을 실시간 확인
② CC 담당자 관점: 자신의 예산 소진 현황을 Fiori 앱에서 즉시 조회
③ 컨트롤러 관점: 월 마감 후 실적을 SAC로 즉시 가져와 다음 Rolling Forecast 수립
④ CFO 관점: 전사 계획·실적·예측을 단일 플랫폼에서 드릴다운
💬 고객사 컨트롤러가 "매월 마감 후 실적을 SAC로 가져와 나머지 기간을 재예측하는 Rolling Forecast를 하고 싶다"고 합니다. 이 루프에서 추가로 설계해야 할 것은 무엇입니까? +
3가지 추가 설계가 필요하다.

① 월별 VERSN 체계: Rolling Forecast는 월마다 새로운 계획 버전을 생성한다. "RF_2025_M01", "RF_2025_M02" 등 버전 명명 규칙과 VERSN 매핑을 사전 설계해야 한다.

② 역전기 자동화: 매월 Write-Back 전 이전 RF 버전의 미래 기간 데이터를 역전기하는 로직이 필요하다. 수동 처리 시 오류 위험 高.

③ SAC Data Action 자동화: 실적 확정 기간은 Actual로 Lock, 미래 기간은 자동 재계산하는 Data Action 스크립트를 설계한다. 이 부분이 Rolling Forecast의 핵심 자동화 포인트다.
