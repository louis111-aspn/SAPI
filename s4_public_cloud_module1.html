Clean Core 원칙이란
SAP S/4HANA Public Cloud의 핵심 설계 철학. 표준 코드베이스를 보호하기 위해 고객사의 ABAP 직접 수정을 원칙적으로 차단한다. 확장은 반드시 BTP(Business Technology Platform) 위에서 Side-by-Side 방식으로만 허용된다. 빠른 업그레이드 적용과 SaaS 운영 효율이 목표이지만, 이것이 곧 CO 기능 제약의 직접 원인이다.
컨설턴트 함정
On-Premise 경험을 가진 컨설턴트가 Public Cloud 프로젝트에 투입될 때, "당연히 되겠지"라고 가정하는 기능의 상당수가 실제로는 지원되지 않는다. 프로젝트 초기 요건 수집 단계에서 반드시 에디션 확인이 선행되어야 한다.
실무 포인트
고객사가 "S/4HANA 도입하겠다"고 말할 때, 첫 번째 질문은 반드시 "어느 에디션입니까?"여야 한다. 에디션에 따라 가능한 설계 범위가 근본적으로 달라진다.

💬 고객사 CO 담당자가 "우리는 IT·HR 공통비를 각 사업부에 순환 배부하는 구조를 쓴다"고 합니다. Public Cloud 도입 시 무엇을 먼저 확인해야 합니까? +
핵심 확인 포인트: "순환 배부"는 Iterative Allocation을 의미하며, Public Cloud에서 미지원이다. 먼저 배부 단계 수와 순환 구조 여부를 확인한 뒤, Assessment/Distribution 방식의 단순화로 요건을 충족할 수 있는지 논의해야 한다. 불가능하다면 PCE 또는 BTP Extension을 검토해야 하며, 이것은 에디션 선택에 영향을 주는 요소다.

Soft Control — 전기 차단 불가
💬 공기업 고객사가 "예산 초과 시 구매 발주가 시스템에서 막혀야 한다"고 요구합니다. Public Cloud Commercial 에디션으로 대응 가능합니까? +
결론: 불가능하다. Hard AVC(Availability Control)는 FM 모듈의 핵심 기능이며, Commercial Edition에서는 미지원이다. WBS Budget Control로 프로젝트성 지출은 일부 통제할 수 있으나, 운영비 전반에 대한 구매 오더 차단은 불가능하다. 이 요건이 필수라면 Public Sector Edition 또는 PCE/On-Premise를 검토해야 하며, 이것을 프로젝트 초기 단계에서 고객사 의사결정권자에게 명확히 전달해야 한다.

ACDOCA / ACDOCP 구조 — Universal Journal의 이해
SAC Planning에서 S/4HANA로 Write-Back할 때 데이터가 어디에 쌓이는지 이해하는 것이 Module 2의 핵심 전제다.
Universal Journal이란
S/4HANA의 단일 실적 테이블 구조. 기존에 FI, CO, AA, ML 등 각 모듈에 분산되어 있던 전표 데이터를 ACDOCA 하나로 통합한 것이 핵심이다. "하나의 진실(Single Source of Truth)"이 가능해졌다.

ACDOCP를 이해해야 하는 이유
SAC Planning에서 작성한 계획 데이터를 S/4HANA에 반영하려면 결국 ACDOCP에 써야 한다. 이 테이블에 기록되지 않으면 S/4의 Plan/Actual 비교 보고서에 전혀 나타나지 않는다. Write-Back의 유일한 표준 타겟 테이블이다.
ACDOCA vs ACDOCP 핵심 차이
ACDOCA는 실제 발생한 전표 데이터(Actual). ACDOCP는 계획 데이터(Plan). 구조는 거의 동일하나 ACDOCP에는 VERSN(계획 버전) 필드가 추가되어 있으며, VRGAR='F'로 고정되어야 한다. 이 두 가지를 잘못 처리하면 계획 데이터가 전기되어도 보고서에 반영되지 않는 문제가 발생한다.
Section 1-6
도입 적합성 판단 프레임
고객사 요건 수집 후 Public Cloud 적합 여부를 판단하는 구조화된 프레임워크. 체크리스트를 완성하면 에디션 권고안이 도출된다.
✅ Public Cloud Commercial 적합 조건
□표준 SAP 프로세스를 수용할 의지와 경영진 의지가 있다
□비용 통제 구조가 Cost Center / Profit Center 중심의 단순 구조다
□제조업 비중이 낮거나 단순한 표준원가 구조다 (서비스업, 유통업)
□Costing-Based CO-PA가 현재 없거나 Account-Based로 전환 가능하다
□6~12개월 이내의 빠른 Go-Live가 최우선 목표다
□예산 초과 시 경고(Warning)만으로도 통제 가능하다 (Hard Stop 불필요)
⚠️ 주의 깊게 검토해야 하는 조건
□복잡한 공통비 배부 로직이 있다 (Iterative / Template 방식)
□MTO 환경 또는 다단계 BOM을 가진 제조업이다
□Activity Type 기반 내부 서비스 원가 계산이 필요하다
□고객사 고유의 차이 분석 로직이 KOB3 수준 이상으로 복잡하다
❌ PCE / On-Premise 검토 권고 조건
□예산 초과 시 구매/회계 전기 차단(Hard AVC)이 필수 요건이다
□공공기관으로 예산회계법 적용 대상이다 (Earmarked Funds, Budget Transfer 필요)
□Costing-Based CO-PA 기반 수익성 분석이 핵심 경영 KPI다
□ABAP 기반 커스터마이징이 불가피한 비즈니스 고유 로직이 있다
□Activity-Based Costing 구조가 원가 관리의 핵심이다
자기 점검 체크리스트 — 이 모듈에서 습득한 핵심 역량
✓
S/4HANA 3가지 에디션(On-Premise, PCE, Public Cloud)의 핵심 차이를 설명할 수 있다
✓
Public Cloud에서 미지원되는 3대 CO 기능(Costing-Based CO-PA, ABC, FM Hard AVC)을 즉시 말할 수 있다
✓
Assessment와 Distribution의 차이, 그리고 Iterative가 왜 미지원인지 설명할 수 있다
✓
FM 모듈이 Commercial Edition에서 미지원임을 알고, 3가지 대안의 한계를 설명할 수 있다
✓
ACDOCA와 ACDOCP의 구조적 차이와 VERSN 필드의 중요성을 설명할 수 있다
✓
고객사 요건 수집 시 Public Cloud 적합 여부를 판단하는 체크리스트를 활용할 수 있다
