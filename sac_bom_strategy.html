01
SAC의 구조적 한계왜 BOM 전개가 SAC에서 어려운가

SAP Analytics Cloud(SAC)는 다차원 OLAP 기반 집계 플랫폼으로 설계되었습니다. 사전 집계된 수치를 계획·분석하는 것이 핵심 철학이며, BOM 전개에 필요한 기능들이 구조적으로 결여되어 있습니다.

필요 기능 SAC 지원 이유
재귀적 BOM 트리 탐색 불가 OLAP 모델은 계층 집계만 가능, parent→child 재귀 불가
품목별 소요량 역산 (MRP 로직) 불가 수식 엔진이 cell-by-cell 연산, 행간 의존관계 처리 불가
수불부 (입고/출고/이월 연결) 부분적 단순 누계는 가능하나 BOM 연동 소요량과의 실시간 연결 불가
공정 Lead Time 반영 불가 시간 축 이동 계산(time-shifted calc) 지원 매우 제한적
다단계 반제품 전개 불가 모델 구조상 최대 2~3 depth에서 실용적 한계 도달
01-B
계획 수불부의 본질ERP에서 받을 수 없는 이유
실적 수불부
  • 이미 발생한 입출고 기록
  • ERP 실적 트랜잭션에서 추출 가능
  • 확정된 과거 데이터
  • 단일 시나리오
계획 수불부
  • 아직 발생하지 않은 미래 소요량
  • ERP에 존재하지 않음
  • 사업계획 생산량 × BOM으로 산출
  • 복수 시나리오 필요
핵심 딜레마 계획 수불부는 사업계획 툴 안에서 생산량 계획을 먼저 세우고, 그것을 BOM에 곱해서 산출해야 비로소 만들어지는 것입니다. ERP에서 가져올 수 없는 구조적 이유가 여기에 있습니다.
국내 대기업도 이 문제를 요구한다 국내 대기업도 SAC-P 도입 시 BOM 엔진을 요구합니다. 이는 SCM 툴 부재의 문제가 아니라, ERP MRP(확정 수주 기반)와 사업계획(가상 시나리오 기반) 수불부가 목적과 데이터 성격이 근본적으로 다르기 때문입니다.
02
글로벌 프랙티스선진 기업들은 어떻게 처리하는가
핵심 결론
글로벌 선진 기업들은 사업계획(FP&A) 툴에서 BOM 전개와 수불부를 직접 구현하지 않습니다. 이 문제는 글로벌에서도 완전히 해결된 사례가 드뭅니다.

글로벌 계획 시스템의 레이어 분리 원칙

재무계획 (FP&A)
SAC · Anaplan · OneStream
⇔
공급망 계획 (SCM)
SAP IBP · Kinaxis · o9
⇔
실행/운영
SAP S/4 PP · ECC MRP

글로벌 FP&A 툴 — Anaplan, OneStream, Adaptive Planning — 은 BOM 전개 엔진을 내장하지 않습니다. BOM 전개가 필요한 경우 글로벌 대기업은 세 가지 방식 중 하나를 선택합니다.

방식 ①
표준원가로 타협
매출수량 × 표준원가 테이블 직접 적용. BOM 전개 없이 재료비 산출.
방식 ②
IBP 연계
S&OP 툴이 BOM 전개 처리 → 집계 결과만 FP&A 툴로 전달.
방식 ③
자체 개발
대기업 내부 IT가 BOM 전개 로직 개발 후 계획 시스템에 연동.
국내 시장의 구조적 특수성 국내 중견·대기업 대부분은 SCM 툴(IBP, Kinaxis 등)이 없습니다. 글로벌 기업은 SCM 툴이 이미 BOM을 처리하기 때문에 FP&A 툴에서 중복 구현할 필요가 없는 구조입니다. 국내 고객의 요구는 예외가 아니라, SCM 시스템 부재를 사업계획 툴이 메우려는 현실적 요청입니다.
02-B
SAP 공식 전략IBP + SAC 이원 구조와 그 공백

SAP의 공식 답은 IBP 단독이 아닌 IBP + SAC 이원 구조입니다.

시스템역할BOM 전개 담당
SAP IBP 운영계획 — 수요, 생산, 공급망, BOM 전개 담당
SAP Analytics Cloud 재무계획 — 매출, 원가, P&L, B/S, Cash Flow 미담당
SAP Datasphere 데이터 통합·거버넌스 미담당
SAP S/4HANA 실적·마스터 데이터 소스 MRP (실행용)
SAP 전략의 공백 IBP를 도입하지 않은 고객 — 국내 중견·대기업 대부분 — 에 대한 SAP의 답이 없습니다. SAP 스스로도 IBP 없이 BOM 전개를 해결하지 못합니다. EASY PLAN이 이 공백을 노리는 것이 시장 기회입니다.
IBP는 S&OP 특화 솔루션 IBP의 핵심 강점은 월 단위 공급망 운영계획(수요계획, S&OP, 재고최적화)입니다. 국내 제조업의 연간 사업계획(Annual Operating Plan)과는 계획 주기, 담당 조직, 목적이 다릅니다. IBP는 연간 사업계획의 직접적 대안이 되기 어렵습니다.
03
선택지 분석아키텍처 옵션별 현실적 평가
옵션 기술 가능성 비용 ERP 리스크 판정
SAC Data Action 유사 BOM 로직 단층 BOM 한정 낮음 없음 패키지 불가
SAC Custom Widget BOM 엔진 기술적 가능 개발비 높음 없음 TCO 비효율
HANA Cloud 별도 인스턴스 최적 매우 높음 없음 중견기업 불가
S/4 HANA 공유 활용 높음 낮음 심각 ERP 안정성 위험
SAP IBP 연계 높음 IBP 라이선스 추가 없음 대기업 한정
Excel 브릿지 (임시) 높음 낮음 없음 단기 브릿지
BTP 경량 엔진 + AI 오케스트레이션 높음 중간 없음 중장기 유력
S/4 HANA 공유 사용의 구조적 위험 연간 사업계획용 BOM 전개는 배치성 대용량 연산입니다. ERP의 OLTP 워크로드와 성격이 충돌하며, HANA 메모리 대량 점유 → ERP 트랜잭션 응답 지연 → 생산/구매/물류 실시간 처리 영향 → 최악의 경우 HANA 인스턴스 다운이 발생할 수 있습니다. SAP도 이 구성을 권장하지 않습니다.
전략적 결론
기술적으로 안전하고, 비용도 합리적이고, 성능도 충분하고, 모든 고객에게 적용 가능한 BOM 전개 아키텍처는 현재 존재하지 않습니다. ABAP 기반 Add-on 방식이 시장에서 살아남는 이유는 해법이 완벽해서가 아니라 대안이 없기 때문입니다.
04
AI 활용 전략BOM 전개 문제를 AI로 우회·보완한다
전략적 전환점
경쟁 구도를 바꿉니다. "BOM 전개 엔진을 누가 더 잘 만드는가"에서 "BOM 없이도 재료비 계획을 얼마나 정확하게 낼 수 있는가"로 — EASY PLAN만의 새로운 게임.

전략 1 — AI 기반 재료비 Driver 예측 (BOM 전개 우회)

실적 데이터 학습으로 소요량 직접 예측
학습 데이터: 과거 3~5년 생산량 실적 + 실제 재료비 실적 ↓ ML 모델: 생산량 → 품목군별 재료 소요량 예측 ↓ 출력: 계획 생산량 입력 시 → 재료별 소요량·금액 자동 산출 + 예측 신뢰구간 (±%)

BOM 구조를 명시적으로 전개하지 않아도, 과거 실적 패턴에서 생산량-재료비 관계를 학습해서 예측합니다. 과거 실적이 충분히 쌓인 대기업에서 오히려 BOM 전개보다 더 정확할 수 있습니다.

전략 2 — 경량 BOM 전개 엔진 + Claude AI 오케스트레이션

AI가 전후를 담당, 연산은 경량 엔진
[사용자] "내년 매출계획 기준으로 재료비 시나리오 3개 만들어줘" ↓ [Claude AI] ① 매출계획 → 생산계획 변환 로직 판단 ② BOM 전개 범위·깊이 결정 (전체 vs 주요 품목) ③ 경량 BOM 전개 엔진 API 호출 ④ 결과 해석 + 이상값 감지 ⑤ 시나리오별 재료비 차이 설명 생성 ↓ [출력] 계획 수불부 + 재료비계획 + 자연어 해설 보고서

전략 3 — 유사 BOM 기반 신제품 재료비 추정

기존 시스템이 전혀 해결하지 못하는 영역

신제품 X의 BOM이 아직 확정되지 않은 경우, AI가 기존 유사 제품의 BOM 패턴에서 신제품 X의 예상 소요량을 추정합니다. 담당자가 검토·수정 후 사업계획에 반영하는 방식으로, BOM 전개 엔진과 AI의 조합이 만드는 완전히 새로운 기능입니다.

계획 BOM 개념 — 핵심 설계 원칙

ERP BOM (실행용)
완제품 A
├ 반제품 B (수율 98%)
│ ├ 원료 C (0.523kg/ea)
│ ├ 원료 D (0.112kg/ea)
│ └ 부재료 E (0.034kg/ea)
└ 포장재 F (1ea)
계획 BOM (사업계획용)
완제품 A
├ 주원료군 (C+D 합산)
│ 0.635kg/ea
└ 부자재군 (E+F 합산)
  단가 기준 처리

레벨과 품목 수를 줄이면 연산량이 기하급수적으로 감소합니다. ERP BOM의 완전한 복제가 아닌 "계획 BOM"으로 충분하며, 이것이 ERP 리스크 없이 경량 구현이 가능한 핵심입니다.

BOM 전개 엔진 핵심 코드 (Python)

def explode_bom(product_plan: dict, bom_master: dict) -> dict: """ product_plan : {제품코드: {월: 생산계획량}} bom_master : {제품코드: [{원료코드, 소요량, 단위}]} return : {원료코드: {월: 소요량}} """ result = {} for product, monthly_plan in product_plan.items(): bom = bom_master.get(product, []) for component in bom: mat_code = component['material_code'] qty_per = component['quantity_per'] if mat_code not in result: result[mat_code] = {} for month, plan_qty in monthly_plan.items(): result[mat_code][month] = ( result[mat_code].get(month, 0) + plan_qty * qty_per ) return result # 수만 SKU × 12개월 → 수초 내 처리 (ABAP 대비 압도적 성능)
